SYS·01  //  SOURCE & ECHO STACK FRAME

How we build the AI-prompt set we track for a client

Prompt Radar decides which buyer questions to track inside AI answers, and proves whether the brand is cited, per engine, every day. It rests on two things a rival can't assemble. First, demand data mined from behind the client's own walls, not the public keyword data everyone can buy. Second, a selection method that mirrors how generative engines actually retrieve, by observing the real question fan-out instead of guessing it. Private questions in, engine-tested prompts out, measured against a fixed baseline. Shown here on one feature of a data-governance platform: column-level lineage.

// stage_1 · data_sourcesMANY IN · public + first-party walled-garden

Objective: assemble demand from every question-carrying source, weighted to the client's own first-party data. Why it matters: public keyword data is a blind spot. It shows only what is already high-volume and typed into a search box, missing the natural-language questions buyers put to AI and everything held behind the client's walls. Using primary, first-party information corrects that blind spot, and it cannot be copied because no competitor or tool can see it.

// action · normalizebuilds stage 2 from stage 1

What this is: an action between stage 1 and stage 2, not a stored table. Objective: merge every stage-1 source into one pool, drop duplicates, and group what remains into ranked topic clusters (that is stage 2). Why it matters: questions arrive from many systems, overlapping and unstructured; this is the step that turns scattered signal into the clean set of topics the rest of the pipeline runs on. Without it there is no way to guarantee coverage or set priorities.

// stage_2 · topic_clusters~40–60 clusters, organized by product

Objective: organize the topics by the client's own products, and guarantee every product a floor of coverage. Why it matters: clustering by popularity alone over-serves the big topics and starves the rest, so whole product lines go invisible in AI answers. Compartmentalizing by product fixes that. // action · overlay + observehow a topic becomes real questions

Objective: turn a generic topic into this buyer's real questions, then capture the sub-questions engines actually generate. Three overlays are applied together — the client's buyers (ICP), their product taxonomy, and their market and competitors — so every tracked question is this buyer's, about this product, in their competitive context. Why it matters: guessing the fan-out tracks the wrong questions; reading the real fan-out through these overlays is the rare step that makes the set match how engines truly assemble an answer.

// stage_3 · query_fan-outthis cluster → ~15–25 prompts

Query fan-out is the set of sub-questions an AI engine invents from one question before it answers. Objective: capture the full branch set one topic explodes into. Why it matters: brands compete at the sub-question level, not the headline phrase, so you have to be present on every branch to appear in the answer. We read the real branches, tagged by where each came from, never guessed.

// action · prioritizethe same rule every time, defensible to a client

Objective: narrow the 300+ universe to the tracked tier by a fixed, coded rule. Why it matters: it removes opinion. The same inputs always produce the same priorities, and every tracked prompt is non-branded, likely to earn a recommendation, spread across the funnel, and defensible to the client.

gate → rank → diversify
1 · gate
Keep only non-branded questions where engines actually name vendors. The rest route to the content plan.
2 · rank
Order by demand × winnability × product & buyer fit. A high-intent, low-volume question can still reach the top.
3 · diversify
Spread across the funnel; collapse any two prompts that are really one bet (same answer, same sources).
